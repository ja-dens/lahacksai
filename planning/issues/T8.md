## Outcome

Build the user-approved optional Fetch/ASI:One demo: retrieve an already saved explanation and record voluntary exchange-specific feedback. This separate entry point never becomes a requirement for automatic Photon explanations.

## Concrete user prompts and actions

1. "Explain the sticker in saved demo exchange demo-3." Resolve the saved exchange/window within the authenticated demo user's scope and return its stored explanation, contextual cue and caveat. Do not reinterpret the image or retrieve the entire chat.
2. "Mark interpretation one as helpful for demo-3." Record a first-choice recipient judgment tied to that saved window and return a receipt. A second-choice selection is valid only if an alternative was shown. Feedback is not sender-confirmed meaning or future live model memory.

## Ownership and independent boundary

Role D denotes a separately delegable task, not a requirement to recruit a fourth person; preserve actual assignees. Own src/adapters/fetch_agent.py, tests/test_fetch_agent.py, docs/FETCH_AGENT_DEMO.md and optional Fetch-specific dependency configuration coordinated with T0. Do not edit Photon ingress, the core context builder or another teammate's codex/fetch-ai-setup branch.

Use a fake backend that implements `get_explanation(window_id, authenticated_recipient_id)` and `save_feedback(window_id, authenticated_recipient_id, selection, note=None)`. The trusted transport/session supplies authenticated_recipient_id; tool arguments/model output cannot choose another recipient. Input: shared synthetic lookup/feedback fixtures. Output: a stored-explanation response or a feedback receipt; missing/unauthorized windows return a safe error.
